### 1.1 G0 的具体产出

- 对 ActionDirector、加载器、存档、回放、AI 分别记录“复用 / 适配 / 暂缓”、依赖和测试；优先复用经过比较的时间线与存档代码。
- 当前 `/assets/models/{type}_{camp}.glb` 与备份的资产命名分别映射，确定迁入方案后再调整 manifest。
- 确定 14 个最终资产键；骑手、车兵、炮手和弓手归入所属成品，不增加最终棋子类型或成品数量。
- 为每枚成品登记选定的参考图、作者/工具、生成批次、来源和待确认许可信息。人脸图、无脸身体图、整体三视图用途分开，定稿后记录版本，避免跨批混用。
- 记录 Blender、导出器、压缩工具和运行时解码器的实际版本；执行一次源工程到 GLB 的重建检查，不沿用其他电脑“已安装”的结论。

### 1.2 G1 的具体产出

G1 使用最小骨骼和压缩测试资产验证运行时，不等待正式精修样板。此阶段先提供局面替换的取消接口及独立测试，存档、FEN、回放的完整产品入口在 M4 接入后再做端到端验收。

- 棋盘与回退棋子先可操作；每个模型的等待和错误独立处理。404、超时、损坏 GLB、几何解码失败、KTX2 转码失败均不影响其他棋子。
- 初始重试策略：单次请求超时 8 秒、最多 2 次自动尝试；等待和失败期间持续显示可操作回退，提供手动重试。总请求时长、退避和缓存失效规则写入实现配置并测试。
- 已卸载或已被新局面替换的异步结果不能重新挂载旧棋子；同一 URL 的资源请求去重，故障缓存可以按明确规则重试。
- 接入 `MOVE_ACCEPTED → ATTACKER_START → CONTACT → TARGET_HIT → TARGET_REMOVE → SETTLE → TURN_READY`。音效、受击、移除由事件驱动，目标保留至 `TARGET_REMOVE`。
- 悔棋、重开、恢复、FEN 导入、回放和卸载均取消旧时间线；任何旧回调不得改变新局面。完整、简洁、关闭特效及减少动态效果模式使用统一取消语义。
- 带骨骼 GLB 的每个棋子有独立骨架与播放状态；静态模型的 `scene.clone(true)` 不能直接作为绑定模型方案。资源可共享，实例播放和释放责任需明确。
- 接入 KTX2 转码器及硬件支持检测；几何压缩在样板比较后选定默认路线。解码器随项目部署，测试加载失败与降级。
- 建立资产清单字段、校验输出和按整帧统计性能的方法，G2 即开始使用。
- 测量现有混合开局；必要时先优化素模的静态网格和基础阴影成本，避免将场景本身的性能缺口留给精修样板承担。

## 2. 样板资产规范

| 项目 | 样板初始约束 | 验证方法 |
| --- | --- | --- |
| 单位、原点、朝向 | 米制；原点在底座底面中心；模型面向 Three.js +Z，阵营朝向由运行时统一处理 | 在实际棋盘核对比例、红黑朝向和最终格点位置 |
| 尺寸与辨识 | 底座直径 ≤0.92 m；保留可读汉字；全身及动作范围需适配格距 | 远、中、近和顶视检查包围盒、邻格遮挡与触控命中区域 |
| 面数 | LOD0 ≤20k、LOD1 ≤8k、LOD2 ≤3k 三角面 | 上限检查；满足画面效果即可，不为达到区间增加面数 |
| 材质与绘制单元 | 每枚 ≤2 个材质；主视图目标 ≤2 个绘制单元，机械组合暂按 ≤4 个验证 | 合并兼容静态部件、使用共享图集，保留必要可动件；仍须通过整帧预算 |
| 骨架 | 每枚成品总骨骼 ≤60 根；人形、四足、机械分别定义兼容结构 | 骨架命名、权重、附属件和极限姿态检查；兼容模板内才共享动画 |
| 纹理 | 本轮棋子 Base Color 源图 8K，桌面高画质 4K/移动 2K；环境表面源图 4K；辅助 PBR 图记录实际分辨率，运行版 KTX2/Basis | 源图与平台版本分开；核对 UV、色彩空间、法线、通道、mipmap、转码格式及整盘内存 |
| 动画 | `idle`、`selected`、`move`、`attack`、`hit`、`death`、`victory` | 片段名称、循环方式、过渡、关键事件时刻逐项登记与播放 |
| 位移 | 格点轨迹由表现时间线驱动，骨骼动作叠加在棋子内部 | 根运动与格点插值不重复位移；结束时精确对格 |
| LOD | 每个资产交付 3 档；切换有滞回，兼容骨架/动作映射 | 连续改变距离时无抖动、动作重启、骨架串台或明显跳形 |
| 压缩 | 样板比较 Meshopt / Draco 后固定一种默认几何路线 | 记录包体、解码耗时、工具版本、参数及加载失败测试 |
| 可重建性 | 源工程、导出配置、清单和来源记录齐全 | 使用记录的命令重建并通过同一校验，不能只交付最终 GLB |

骨架与图集规范在 G2/G3 通过后冻结。确需例外时，先记录该资产与整盘测量结果、原因和规范版本，再决定是否采用；不能只提高数字上限掩盖整盘性能问题。

## 3. G2/G3 完整样板验收

### 3.1 参考图与制作路线

当前红帅完整参考图为 [`象棋3D参考图-备份/三视图合并/帅-红方-三视图.jpg`](../象棋3D参考图-备份/三视图合并/帅-红方-三视图.jpg)。解压目录为本地资料，版本库中的可恢复来源是 [`象棋3D参考图-备份.zip`](../象棋3D参考图-备份.zip)；新环境先解压到同名目录。原计划中的 `象棋3D参考图/三视图合并/帅-红方-三视图.png` 不作为当前输入路径。

人形、马、象可使用图生 3D 生成候选高模，再完成拓扑、比例和结构处理；车体、炮体、武器和底座继续采用可控的参数化制作。生成工具在样板阶段记录输入、设置、费用、耗时、可编辑性及来源信息后比较，不以“最高面数”作为质量或通过标准。

Meshy 的批量候选客户端、离线测试及 3000 积分预算见 [API Demo](MESHY_API.md)。按现有整件参考图生成的马、车、炮候选用于造型评估，复合结构仍须按 G3 拆件验证；API 生成成功不自动将本表的造型、绑定或成品验收状态改为通过。

Meshy 候选 GLB 放在 `assets/generated/meshy/<资产键>/v<版本>/`；整理与验收文件使用独立修订子目录。红帅 v1 已实际生成。原始生成结果与整理后的源工程分别保留，运行时只接入经过校验和用户认可的导出物。

- [ ] 按第 6 节完成桌面与移动设备测试；无法满足预算时先优化样板或基础场景，再开放批量制作。

### 3.3 马与炮的结构验证

- 马验证四足关节、骑手/武器/马尾挂接、踏步或跃击，以及低档 LOD 的权重和形体；同时核对象鼻、象耳等差异是否需要补充局部验证。
- 炮验证炮管后坐或抛臂/配重等结构的运动范围、回位与独立挂点；红黑结构差异按所选参考图核对，不能用一套机械结构的结论覆盖另一套。
- 使用低成本结构和短动作完成验证，不提前承诺这些验证件已达到成品标准。结果反映到骨架模板、绘制单元预算、事件时刻与批量工作量中。

## 6. 统一性能与可靠性验收

### 6.1 测试条件

- 记录提交、资产版本、设备 CPU/GPU/内存、系统、浏览器、视口、DPR、特效、相机、LOD、温度或持续运行时长、缓存和网络条件。
- 目标设备沿用二期开发方案的中档桌面、集显电脑、Android 和 iPhone/Safari；桌面模拟手机视口只用于布局与交互，不替代移动硬件报告。
- 样板、每批、最终发布使用同一采样方法：预热 30 秒，分别采集开局静止、相机操作和走子/吃子各 60 秒，重复 3 次；冷启动单独测量。
- 从合法测试局面反复执行“吃子 → 悔棋/恢复 → 再吃子”，累计至少 50 次，另做连续重开/卸载检查；不要求一盘棋实际吃掉 50 枚棋子。

### 6.2 门槛与统计口径

| 项目 | 桌面 | 移动端 | 口径 |
| --- | --- | --- | --- |
| 帧时间 | P95 ≤20 ms，目标 ≥50 FPS | P95 ≤33.3 ms，目标 ≥30 FPS | 报告 P50/P95/最大值及超预算帧比例，保留操作场景 |
| Draw Call | 整帧 ≤180 | 整帧 ≤120 | 累加主视图、阴影、离屏/后处理通道；同时列分通道数据 |
| GPU 资源 | 目标 ≤400 MB | 目标 ≤220 MB | 说明工具或估算公式；下载字节数、JS 堆与显存分别记录 |
| 冷启动可操作 | ≤4 秒 | ≤4 秒 | 以回退棋子可完成合法走子为准；参考网络下行 10 Mbps、上行 2 Mbps、RTT 100 ms |
| 连续操作 | 无持续增长 | 无持续增长 | 记录几何体、纹理、材质、骨架实例、播放实例和计时器数量；区分固定缓存与泄漏 |

基础场景未达标时，先处理静态网格合并、图集、LOD、DPR 和阴影更新频率，再继续增加精修资产。几何压缩控制传输成本，不能当作自动降低绘制次数或动画计算成本的证明。

### 6.3 自动化与留档

- 资产检查覆盖本阶段实际交付范围；G2 校验样板的七段动画和三档 LOD，批次校验本批，E5 校验完整 14 键和 42 文件。
- 单元测试覆盖事件顺序、取消、重试和资源状态；浏览器覆盖真正的 GLB/解码器故障、可操作回退、多个动画实例及局面替换。
- 现有 Playwright 用例主要验证正常场景、布局与走子，不能代替上述新增门槛；实施对应功能时补测试。
- 每次验收留存结构化资产检查结果、性能原始采样、截图、设备和提交信息；报告输出位置在 G0 确定并在后续保持一致。
